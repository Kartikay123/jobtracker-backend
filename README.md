# JobTracker Backend

FastAPI · PostgreSQL · Redis · arq workers · Docker

## Local development

```bash
cp .env.example .env
docker compose up -d --build
```

API at http://localhost:8000 — interactive docs at `/docs` and `/redoc`.

```bash
docker compose ps               # service status
docker compose logs api -f      # tail api
docker compose logs worker -f   # tail background worker
docker compose down             # stop (DB persists)
docker compose down -v          # stop and wipe DB volume
```

### Common dev tasks

```bash
# Database migrations
docker compose exec api alembic revision --autogenerate -m "msg"
docker compose exec api alembic upgrade head
docker compose exec api alembic check         # are models in sync with DB?

# psql / redis-cli
docker compose exec db psql -U jt -d jobtracker
docker compose exec redis redis-cli

# Tests
docker compose exec api pytest               # full suite
docker compose exec api pytest -v -s         # verbose, show prints

# Manually trigger background tasks
TOKEN=...
curl -X POST localhost:8000/api/admin/scan-followups \
  -H "Authorization: Bearer $TOKEN"
```

## Project layout

```
app/
├── main.py            # FastAPI app + lifespan
├── core/              # config, security (JWT/bcrypt), redis, cache, rate_limit, queue
├── db/                # SQLAlchemy engine, session, base, mixins
├── models/            # ORM classes
├── schemas/           # Pydantic request/response schemas (CamelModel)
├── api/v1/            # routers (auth, jobs, analytics, ai, interview, admin)
├── services/          # business logic (ai_client, resume_parser, analytics, email)
└── workers/           # arq task definitions
alembic/               # database migrations
tests/                 # pytest suite
```

## Deployment

### Render (recommended — Blueprint)

1. **Push this repo to GitHub.**
2. **On Render → New → Blueprint → connect repo → Apply.**
   `render.yaml` provisions four services: api, worker, Redis, Postgres.
3. **Set CORS_ORIGINS** on the api service to your deployed frontend URL
   (Render dashboard → jobtracker-api → Environment).
4. Visit the api's public URL → `/health` should report all green.

`JWT_SECRET` is auto-generated by Render. Postgres `DATABASE_URL` and Redis
`REDIS_URL` are wired automatically by the blueprint.

### Railway (manual)

Railway has no equivalent of `render.yaml`. Steps:

1. New project → "Deploy from GitHub" → select this repo.
2. **Add a Postgres plugin** → Railway sets `DATABASE_URL` automatically.
3. **Add a Redis plugin** → Railway sets `REDIS_URL` automatically.
4. **Add a second service** for the worker:
   - Same repo, same Dockerfile.
   - Set `Start Command` to: `arq app.workers.worker.WorkerSettings`
   - Set `SKIP_MIGRATIONS=1` (the api service runs them).
5. **Set the rest of the env vars** on both services:
   ```
   ENVIRONMENT=production
   JWT_SECRET=<generate with: python3 -c 'import secrets; print(secrets.token_urlsafe(48))'>
   JWT_ALGORITHM=HS256
   JWT_EXPIRE_MINUTES=60
   CORS_ORIGINS=https://your-frontend.vercel.app
   WEB_CONCURRENCY=2
   ```

### Frontend (Vercel / Netlify)

The frontend is a separate folder (`project/Frontend/`). Deploy it to Vercel
or Netlify and set:

```
VITE_API_BASE_URL=https://your-backend.onrender.com/api
VITE_AI_ENABLED=true
```

After the frontend is live, copy its URL into the api's `CORS_ORIGINS`.

### Post-deploy checklist

- [ ] `https://<api>/health` returns `database: ok`, `redis: ok`
- [ ] `https://<api>/docs` loads
- [ ] Sign up via the frontend works
- [ ] Worker logs show `cron:scan_stale_jobs` registered
- [ ] (Optional) Run `docker compose exec api alembic current` locally with prod
      `DATABASE_URL` to verify migrations ran

## Image variants

The Dockerfile is multi-stage. Local compose uses `target: dev`
(uvicorn `--reload`). Render/Railway build the default last stage (`prod`),
which:

- copies installed packages from the deps stage (no `build-essential` in final image)
- runs as non-root user `app`
- runs `entrypoint.sh` → `alembic upgrade head` → exec gunicorn (or arq)

```bash
docker build --target=prod -t jobtracker-api:prod .
docker images jobtracker-api    # ~200 MB vs dev's ~600 MB
```

## Plugging in a real AI provider

`app/services/ai_client.py` is currently a deterministic stub. A complete
example for swapping in OpenAI is at the top of that file. The function
signatures and return shapes are stable, so the API layer (rate limiting,
DB persistence, response schemas) doesn't change.

For latency reasons, when you switch to a real provider, also move the AI
calls to the arq worker (the same pattern Step 9 used for email reminders)
so the HTTP request doesn't block for 30 seconds.
